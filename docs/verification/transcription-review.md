## Findings

### R1 — P2: disabled generation also hides access to persisted transcripts

**ADDRESSED on scoped re-review.** The original `apps/mobile/src/features/transcription/GenerationPanel.tsx:100` rendered the only recording-detail sign-in card only when `capabilities.available` was true. Reproduce by completing a transcript, reloading the browser (development credentials are held in memory), then opening that recording with provider credentials disabled on the API. The screen offered the unconfigured message and a status check, but no sign-in path to read the existing server transcript. The status check did not authenticate. The user would have had to discover another screen's sign-in path.

The backend already permits authenticated GET with the provider disabled (`apps/api/src/transport/http/recording-routes.ts:59`), and `transcription-controller.ts:129` reads existing records for a signed-in actor regardless of generation capability. The corrected panel exposes **View saved transcript** while signed out/unconfigured (`GenerationPanel.tsx:101`), then reveals sign-in with saved-result wording (`:108`). Generation/retry remain gated by capability. A new controller regression explicitly restores a complete result while capability is false. Root reported browser verification of the optional access button and is checking the full persisted-result scenario separately; this reviewer verified the source correction.

### R2 — P1: Expo native fetch replaces the required upload content type

**ADDRESSED on scoped re-review.** The original `apps/mobile/src/services/recording-upload.native.ts:18` returned an Expo `File` directly to `expo/fetch`. The installed Expo implementation normalizes any Blob/File to bytes and sets `overriddenHeaders` to `Content-Type: body.type` (`apps/mobile/node_modules/expo/src/winter/fetch/RequestUtils.ts:71`); `fetch.ts:65` applies those headers after the client's headers. Saved native audio retains an `audio.mp3`, `audio.m4a` or `audio.wav` filename (`file-recording-store.ts:65`), and native `File.type` comes from that extension. Consequently the original native upload sent an audio MIME type despite the processing client's `application/octet-stream` header. The API requires exactly the latter in `recording-routes.ts:82` and would return 415 before accepting audio.

The reviewer independently executed the installed `normalizeBodyInitAsync` and `overrideHeaders` functions with an `audio/mpeg` Blob and an explicit octet-stream input header. Output was `{"headers":[["Content-Type","audio/mpeg"]],"bytes":[1,2,3]}`. This is a deterministic dependency-boundary reproduction, not a physical phone upload. Client tests that supply a plain mock fetch skip the offending normalization.

The corrected native preparation awaits `file.arrayBuffer()` (`recording-upload.native.ts:21`) and checks cancellation again before returning the prepared bytes (`:22`). Expo's ArrayBuffer normalization does not override the explicit binary content type. The new `apps/mobile/test/transcription-native-upload.test.ts:82` executes the native preparation and shared client against a real temporary file, substitutes the unavailable device filesystem/HTTP bridges, and executes the installed Expo normalization/header functions. Its assertions cover final octet-stream content type, retained authorization and exact binary bytes (`:98`). The mobile worker reports this regression first reproduced `audio/wav` in place of octet-stream and then passed after the fix; this reviewer inspected the source and test without rerunning the already-passing suite.

`docs/verification/transcription-mobile.md` now explicitly describes full-file native buffering, the non-interruptible file read and the post-read cancellation check. Physical phone memory/upload acceptance remains unverified; this correction does not claim a streaming native transport or safe near-limit memory behavior on every phone.

### C1 — nonblocking specification clarification: title is display metadata

**CLARIFIED.** Registration compares immutable filename and size, while retaining the initial server title (`apps/api/src/modules/recordings/service.ts:24`). The integration test deliberately accepts a local title change (`apps/api/test/processing.integration.ts:67`). The initial design's phrase “conflicting metadata fails” was broader than this behavior. Root confirmed that local renaming must not strand a recoverable recording, and the current design now explicitly states that the title is display metadata; no application change is requested.

## Evidence and limits

The reviewer read the actual tests without rerunning the already-passing suites. Root reported 22 passing tests across the full PostgreSQL integration run; the inspected processing file contains six integration cases using an isolated schema and actual temporary storage. They cover registration/upload idempotency, ownership, persisted completion, ambiguous/recovered submission, retained polling identity, HTTP upload and worker exclusion/recovered uploading. The filesystem test checks exact persisted bytes/hash, short/long upload rejection and pending-file cleanup. These tests use provider doubles; they do not exercise actual Plaud audio decoding or paid transcription.

The provider worker reports 52 passing protocol tests using actual temporary files and injected HTTP responses; their source covers raw multipart boundaries, ETag/MD5/auth behavior, response caps/timeouts, status/result normalization and ambiguous submission. The final mobile/client report records 29 passing focused tests, including the new native-normalization regression; controller source covers restoration, response-loss reconciliation, duplicate taps, polling, actor changes, source release and acknowledged retry. This reviewer did not independently reproduce their runtime counts.

Crash coverage is checkpoint-state recovery plus concurrent workers, not an actual killed-process or disconnected-database fault-injection campaign. The scoped processing tests do not directly exercise the full backoff sequence, 24-hour expiry, unknown COMMIT outcome or shutdown during a provider call. Those are source-inspected paths, not independently demonstrated runtime results. Root browser acceptance and final platform bundles must be recorded separately.

The Plaud transcription skill and current official endpoint documentation were read during this review. The adapter matches the documented token exchange, multipart completion fields, transcription headers and status names: [partner token](https://docs.plaud.ai/api-reference/authentication-api/get-partner-token.md), [user token](https://docs.plaud.ai/api-reference/authentication-api/get-user-token.md), [multipart URL plan](https://docs.plaud.ai/api-reference/file-upload-api/generate-presigned-upload-urls.md), [multipart completion](https://docs.plaud.ai/api-reference/file-upload-api/complete-multipart-upload.md), [submission](https://docs.plaud.ai/api-reference/transcription-api/submit-audio-for-transcription.md), [poll results](https://docs.plaud.ai/api-reference/transcription-api/get-transcription-task.md). The File API documentation names MP3/Opus while the transcription reference names M4A/MP3/WAV; this remains a live compatibility unknown, already stated in `plaud-provider.md`. No live provider calls or physical phone/Plaud hardware checks were made. No new production-security scope is proposed.
